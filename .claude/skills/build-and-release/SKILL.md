# Build and release for SkyGrid-ng

Gradle Kotlin DSL, Java 25 toolchain, Paper 26.1. Shaded plugin jar via the Shadow plugin. Releases
are automated by release-please from the commit history.

## Version catalog (inline)

The version catalog is defined inline in `settings.gradle.kts` (not a `libs.versions.toml`), matching
the OLF convention. Add or bump versions and library aliases there, then reference them as
`libs.<alias>` in `build.gradle.kts`. Renovate keeps versions current using the OLF presets in
`renovate.json`.

## Shadow and relocation

The plugin jar shades Gson and relocates it to `net.onelitefeather.skygridng.libs.gson` to avoid
clashing with the server or other plugins. Keep any shaded library relocated under
`net.onelitefeather.skygridng.libs.*`. The Modrinth and Hangar uploads use `tasks.shadowJar`.

## plugin-yml

`plugin.yml` is generated by the `de.eldoria.plugin-yml.bukkit` plugin from the `bukkit { }` block.
The plugin is a world generator, so it must enable at server startup:

```kotlin
import net.minecrell.pluginyml.bukkit.BukkitPluginDescription
// inside bukkit { }
load = BukkitPluginDescription.PluginLoadOrder.STARTUP
```

The command is `skygrid`, the permission is `skygridng.admin`, the main class is
`...bootstrap.SkyGridNgPlugin`, and the display name is `SkyGrid-ng`.

## Publishing

Three pieces, configured in `build.gradle.kts`, run by the reusable org workflow in CI:

- Modrinth via `com.modrinth.minotaur`: `uploadFile.set(tasks.shadowJar)`. Project id is a
  placeholder until the Modrinth project exists.
- Hangar via `io.papermc.hangar-publish-plugin`: the jar is `tasks.shadowJar.archiveFile`. Slug and
  id are placeholders.
- CycloneDX SBOM via `org.cyclonedx.bom` 3.x: the SBOM is uploaded to Dependency-Track. The 3.x API
  differs from older versions, see the warning below.

### CycloneDX 3.x (do not regress)

CycloneDX 3.x removed the `set*`/`get*` accessors and the `outputFormat`/`destination` properties,
and moved `includeConfigs` from `cyclonedxBom` to the new per project task `cyclonedxDirectBom`. The
correct config is:

```kotlin
tasks.cyclonedxDirectBom {
    includeConfigs = listOf("runtimeClasspath")
}
```

The aggregate `cyclonedxBom` still writes `build/reports/cyclonedx/bom.{xml,json}`, which CI uploads.
Do not reintroduce `setIncludeConfigs(...)` or `setOutputFormat(...)`; those fail configuration on
3.x and break every Gradle invocation (including `runServer`).

## Releasing with release-please and Conventional Commits

The version lives in `gradle.properties` behind a release-please marker
(`version = ... # x-release-please-version`). Never edit it by hand. release-please reads
Conventional Commits to bump the version and write `CHANGELOG.md`:

- `fix:` -> patch, `feat:` -> minor, a breaking change (`!` or `BREAKING CHANGE:`) -> major (minor
  while pre 1.0, because `bump-minor-pre-major` is set).
- `refactor`, `chore`, `docs`, `build`, `ci`, `test` do not trigger a release unless they carry a
  breaking change.

Publishing happens in the release-please workflow after a release PR merges. It calls the reusable
OLF org workflow. See `references/publishing.md` for the workflow tags, the placeholders to fill
before the first publish, and the Dependency-Track path.

## Local testing

Run a test server with `./gradlew runServer` (runPaper). It creates a `run/` directory which is
gitignored, so never commit it. A full build is `./gradlew build`; tests are `./gradlew test`. The
pure core also compiles standalone, see the `hexagonal-architecture` skill `compile-core.sh` for a
fast check without resolving plugins.
