# Build and release for SkyGrid-ng

Gradle Kotlin DSL, Java 25 toolchain, Paper 26.1. Shaded plugin jar via the Shadow plugin. Releases
are automated by release-please from the commit history.

## Multi-module layout

The build is grouped under category folders (see the `hexagonal-architecture` skill for the
responsibilities and the dependency arrows):

- `api`, `ports`, `core`: framework-free `java-library` modules, no platform plugins.
- `adapters/generator`, `adapters/command`, `adapters/json`: the Bukkit/Gson adapter libraries.
- `platforms/common`: the shared Bukkit composition root, a library (no platform plugins).
- `platforms/paper`: the single Paper distribution. Applies shadow, plugin-yml, run-paper, and
  CycloneDX SBOM generation. Produces `skygrid-ng-<version>.jar`.
- `verification`: ArchUnit architecture tests only (no production code). Depends on every production
  module and enforces the hexagonal rules at build time. See the `hexagonal-architecture` skill.

`platforms/paper` depends on `platforms/common`, which also holds the `platforms.olf` package
(OneLiteFeather-specific mechanics like challenges, a naming convention now rather than a separate
distribution; see the `hexagonal-architecture` skill).

The root `build.gradle.kts` is pure aggregation: it sets `group` for all projects and the shared
`version`. The version is read from `gradle.properties` and stripped of the trailing
`# x-release-please-version` marker comment (`substringBefore("#").trim()`) so the jar name and the
publish metadata stay clean. Never put production code or platform plugins in the root build.

Shared build config (Java 25 toolchain, UTF-8, JUnit platform) lives in the `skygrid.java-conventions`
precompiled script plugin in `buildSrc`, which every module applies. `buildSrc` cannot read the
inline version catalog, so the Java version is a literal there: keep it in sync with the catalog.

## Version catalog (inline)

The version catalog is defined inline in `settings.gradle.kts` (not a `libs.versions.toml`), matching
the OLF convention. It is shared automatically with every subproject, so reference entries as
`libs.<alias>` in each module's `build.gradle.kts`. The inline catalog is NOT visible to `buildSrc`
(see above). Add or bump versions and library aliases in `settings.gradle.kts`; Renovate keeps
versions current using the OLF presets in `renovate.json`.

## Shadow and relocation

Shadow is applied in the distribution module only (`platforms/paper`). The shaded jar shades Gson
and relocates it to `net.onelitefeather.skygridng.libs.gson` to avoid clashing with the server or
other plugins. Keep any shaded library relocated under `net.onelitefeather.skygridng.libs.*`.
`platforms/paper` depends on `platforms/common`, which exposes the whole object graph (adapters,
core, ports, api, Guice) with the `api` configuration, so shadow bundles everything transitively
into a self-contained jar. The GitHub release attachment step uses `platforms/paper`'s
`tasks.shadowJar`.

## plugin-yml

`plugin.yml` is generated by the `de.eldoria.plugin-yml.bukkit` plugin from the `bukkit { }` block.
The plugin is a world generator, so it must enable at server startup:

```kotlin
import net.minecrell.pluginyml.bukkit.BukkitPluginDescription
// inside bukkit { }
load = BukkitPluginDescription.PluginLoadOrder.STARTUP
```

The command is `skygrid`, the permission is `skygridng.admin`. The main class is
`...platforms.common.SkyGridNgPlugin` (display name `SkyGrid-ng`), which always wires and enables
the OLF-only mechanics in its `platforms.olf` package too (there is no separate distribution without
them). The `bukkit { }` block keeps `load = STARTUP`. The distribution is not published to any
public plugin registry; the project is OneLiteFeather-internal.

## Publishing

Configured in `platforms/paper/build.gradle.kts`, run by the reusable org workflow in CI:

- CycloneDX SBOM via `org.cyclonedx.bom` 3.x: the SBOM is uploaded to Dependency-Track. The 3.x API
  differs from older versions, see the warning below.

SkyGrid-ng does not publish to Modrinth or Hangar; the project is OneLiteFeather-internal. Internal
Maven publishing may be added later as a separate task.

### CycloneDX 3.x (do not regress)

CycloneDX 3.x removed the `set*`/`get*` accessors and the `outputFormat`/`destination` properties,
and moved `includeConfigs` from `cyclonedxBom` to the new per project task `cyclonedxDirectBom`. The
correct config is:

```kotlin
tasks.cyclonedxDirectBom {
    includeConfigs = listOf("runtimeClasspath")
}
```

The aggregate `cyclonedxBom` still writes `build/reports/cyclonedx/bom.{xml,json}`, which CI uploads.
Do not reintroduce `setIncludeConfigs(...)` or `setOutputFormat(...)`; those fail configuration on
3.x and break every Gradle invocation (including `runServer`).

## Releasing with release-please and Conventional Commits

The version lives in `gradle.properties` behind a release-please marker
(`version = ... # x-release-please-version`). Never edit it by hand. release-please reads
Conventional Commits to bump the version and write `CHANGELOG.md`:

- `fix:` -> patch, `feat:` -> minor, a breaking change (`!` or `BREAKING CHANGE:`) -> major (minor
  while pre 1.0, because `bump-minor-pre-major` is set).
- `refactor`, `chore`, `docs`, `build`, `ci`, `test` do not trigger a release unless they carry a
  breaking change.

Publishing happens in the release-please workflow after a release PR merges. It calls the reusable
OLF org workflow. See `references/publishing.md` for the workflow tags, the placeholders to fill
before the first publish, and the Dependency-Track path.

### CI artifact paths after the multi-module split (verify before the first release)

The reusable org workflows (`gradle-build-pr.yml`, `gradle-plugin-publish.yml`) were written for a
single-module build and the reference copy attaches `build/libs/*.jar` from the repository root. The
shaded jar now lives in `platforms/paper/build/libs/`, so the root `build/libs/` is empty. Before
the first real release, confirm the reusable workflow globs `**/build/libs/*.jar` (or pin a workflow
version that does), or adjust the release artifact path, otherwise the GitHub release attachment
step finds no jar.

## Local testing

Run a test server with `./gradlew :platforms:paper:runServer` (runPaper). run-paper is applied only in
`platforms/paper`, because the run-task build service cannot be registered by two modules at once. It
creates a `run/` directory which is gitignored, so never commit it. A full build across all modules is
`./gradlew build`; tests are `./gradlew test`. Run one module's tests with `./gradlew :core:test`
and a single test with `./gradlew :core:test --tests "...ClassName"`. The framework-free
modules (api + core) also compile standalone, see the `hexagonal-architecture` skill `compile-core.sh`
for a fast check without resolving plugins.
